# AppRivet architecture and decision record

Recorded November 25, 2026, at the 0.4.13 preview release. AppRivet is an independent app builder with a portable Go core, a native Mac app, and local browser frontends on Windows and Linux. It started with an iOS Simulator workflow and added Flutter for people who want one codebase across selected platforms. The repository is public. A redistribution license and commercial model remain undecided. [Product requirements](PRD.md) · [Foundation decision](adr/0001-foundation.md) · [0.4.13 release](https://github.com/fpokrzywa/AppRivet/releases/tag/v0.4.13)

## System architecture

| Layer | Implementation and decision |
| --- | --- |
| Portable core | `cmd/apprivet` and `internal/cli` expose validated commands, stable exit codes and versioned JSON for people and coding agents. The original SwiftUI scaffold is embedded. AppRivet uses its own implementation and official platform tools. |
| Native Mac app | `desktop/AppRivetDesktop.swift` owns the SwiftUI interface and Sparkle update controls. `desktop/Workflow.swift` calls the bundled AppRivet CLI. The app provides project creation, reopening, build controls, Simulator launch, previews and publishing preparation without requiring Terminal for routine use. |
| Windows and Linux launcher | `cmd/apprivet-studio` opens a local browser workspace. `internal/studio` serves the UI on loopback and uses the same Go project and generation logic. Session and request checks protect local actions. AppRivet has no public hosted service. |
| Build and discovery | `internal/build`, `internal/doctor` and `internal/devices` call official tools. `internal/runner` supplies deadlines and bounded, redacted diagnostics. Builds run as the local OS user and can execute project scripts, so they require explicit project trust. |
| Generation and credentials | `internal/generation` prepares bounded requests, validates approvals and materializes provider output. `internal/credentials` and the Mac app's Keychain integration store credentials in the OS vault when available. |
| Publishing preparation | `internal/storebuild` builds and verifies local release artifacts. `internal/storeconnect` persists nonsecret settings and tests store connections. |
| Worker foundations | `internal/snapshot` and `internal/admission` implement portable source verification and offline admission and reservation records. A running remote executor and signing broker remain future work. |

The main workflow is **describe or import → choose project format and targets → review and approve AI requests → save source → review and trust the project → build and preview → prepare a store artifact when ready**. Project creation, model calls, compilation, Simulator launch, and publishing each have their own outcome. ## Project formats, workspace and design

- **Flutter is the shared-code route.** Check iOS, Android, Web, Windows, macOS or Linux to generate those platform folders in one project with shared Dart source and `pubspec.yaml`. The app shows Flutter when it detects the SDK. Windows and Linux can reopen projects while the SDK is absent. The whole project folder can move between hosts for target builds.
- **SwiftUI is the native iOS route.** SwiftUI is Apple's UI framework. Xcode is the development toolchain that builds the project and runs the iOS Simulator. iOS builds continue to need a Mac with full Xcode and a compatible runtime. The Simulator workflow can run without Apple signing credentials. Web builds can run on any supported Flutter host. Android needs the Android SDK. Desktop outputs require the matching OS and SDK. Publishing a SwiftUI-only project on both mobile stores means porting its iOS-specific implementation to Flutter or building and maintaining a separate Android app.
- **The workspace centers on the brief.** **Describe your app** accepts typed text and UTF-8 `.txt`, `.md` or `.markdown` imports. AppRivet keeps the full brief and has no app-level brief length cap. Provider and system limits still apply. Starting in 0.4.13, long text scrolls inside the editor. The browser check imported 624,040 characters at wide and narrow widths with a stable editor height.
- **Projects restore their working context.** **Your projects** opens the selected project and restores the brief, format, platforms, creation method and recorded provider/model. Modern projects save `APP_BRIEF.md` and AppRivet metadata. Existing projects can recover details from earlier brief and target files. Selecting a Flutter Runner project or workspace on the Mac resolves the surrounding Flutter root. Generation protects existing project folders and offers a separate AI project when recovering an offline starter's brief.
- **Build results lead to the corresponding preview.** On the Mac, iOS launches through Simulator, **Open in Browser** serves the built Web app locally, and **Show APK in Finder** opens the Android artifact location. Run that APK in an Android emulator separately. Build and Run uses the source already saved in the project.
- **The visual design uses gradients and the supplied AppRivet mark.** The blueprint treatment was explored and dropped. The header pairs the AppRivet name with a transparent ivory or charcoal emblem for the active theme. The Mac bundle uses the logo for Finder and Dock. **Admin** sits between **Your projects** and **Quit**, with appearance, provider and store settings. The installed release appears in the lower-right corner.

## AI generation and credentials

| Decision | Behavior |
| --- | --- |
| Provider and model are configurable | Admin offers OpenAI and Anthropic with model presets and a custom model ID. Presets include GPT-6.2 Sol, GPT-6.2 Astra, Claude Opus 5.5 and Claude Fable 5.2. Save keys separately by provider. Paste a key or import a UTF-8 `.txt` file containing the key on one line, then save settings. The selected provider's key can be replaced or removed. |
| Explicit approval precedes provider sends | Review the provider, model, platforms and exact prompt before sending it. For staged generation, approve the planning requests first. Review the resulting plan and exact component prompts, destination files and budgets, then approve the code requests once as a group. |
| Large briefs use bounded component planning | Planning is on by default and required above 4,096 UTF-8 bytes. AppRivet splits large input at text boundaries, extracts requirements and synthesizes a plan. It retains the original brief. The plan proposes components and shared interfaces to limit the amount of code asked for at once. |
| Plan truncation has one reviewed retry | At 0.4.12 the plan budget increased to 8,000 output tokens, with one retry at 16,000 for a truncated plan. The preflight budget covers both attempts. Supported Claude Opus and Fable presets use lower reasoning effort for planning. The code prompts keep their own budgets. Context limits, output limits, filtering and other provider failures have distinct handling. |
| AI generation is the default | Earlier offline defaults could produce a working template that appeared to be the requested app. Starting with 0.4.11, new projects default to reviewed AI generation. Offline starters remain selectable for toolchain testing. AppRivet rejects known starter responses and partial or invalid generation. A failed component identifies the failing step and leaves the new project uncreated. |
| Secrets use OS storage | macOS Keychain, Windows Credential Manager and Linux Secret Service hold saved provider keys. The browser launcher offers session-only keys when persistent storage is unavailable. Keys stay out of project metadata, prompt review and build artifacts. macOS may request access to the login Keychain. Access after an update remains a live check. |

Provider tests use fixtures. The project's product acceptance case is a real watchmaker brief that produces a playable app with a working assembled timepiece. A successful compile or template launch confirms the toolchain path. A gameplay check establishes whether generation delivered the requested behavior. ## Store packages and connections

- **Publish** belongs to each project. **Build for Store** runs after the project trust check and records the resulting package, SHA-256 and build history in local AppRivet data outside the source folder.
- **App Store** uses the project's local Xcode signing setup on a Mac. Configure the developer team, distribution identity and profile, then archive and export an App Store Connect `.ipa`. Separately, **Admin → Store Connections** accepts a Key ID and `.p8` API key, plus an Issuer ID for team keys. The connection test checks access to the app list.
- **Google Play** uses Gradle release signing for a Flutter Android project. AppRivet builds an `.aab` and verifies the expected upload certificate fingerprint. Store Connections accepts a service account `.json` key. The connection test verifies token issuance. App and track access are separate live checks.
- Store settings files hold identifiers and fingerprints. Private keys use the OS credential vault. AppRivet prepares packages for manual console upload. Automated submission and production rollout remain future capabilities.

## AppRivet installation, signing and updates

- macOS ships a universal Apple silicon and Intel DMG with a drag-to-Applications workflow. Windows ships a portable ZIP in GitHub Releases. Linux uses the packaged launcher artifact from a successful CI run. The install guide labels published Mac and Windows links with their version.
- AppRivet's own distribution signing is independent of signing a user's project for a store. Starting at 0.4.10, the release workflow signs AppRivet with Developer ID, submits the app and DMG to Apple, staples the accepted tickets and runs Gatekeeper checks. The GitHub `macos-release` environment supplies the Team ID and five signing and notarization secrets to the release job. A first-open confirmation for software downloaded from the internet can still appear in macOS.
- Sparkle checks a public update feed and verifies the update ZIP with AppRivet's release key before extraction. The **AppRivet → Check for Updates…** menu and the main-window button both initiate a manual check. Installation and relaunch require approval. Hosted testing proved download, replacement and relaunch with an automated approval driver. The ordinary dialogs and update from a personal Mac's Applications folder remain hands-on checks.
- For each release, increment the display version and build number, run CI and the signing workflow, sign the exact updater ZIP, publish the verified assets and compare public hashes. Update the install guide and signed archive metadata in the appcast together after the downloads are public. The install-link test checks version alignment. The verification record captures the source revision and run evidence.
- **0.4.13** is the published scrolling fix, with build number 17. The **top-of-hour update check** was implemented and tested separately for the planned 0.4.14 release. It follows the Mac's local clock while the app is running, respects automatic-check settings and skips an hour when Sparkle is already handling an update session. It retains manual approval for installation. A live check in an installed release remains pending.

## Device discovery and worker foundations

| Milestone or decision | Built and verified |
| --- | --- |
| M1 portable CLI | Host checks, original SwiftUI project creation and inspection, and trusted simulator build and test on a Mac. Hosted XCTest validated that path. |
| M2 read-only device discovery | `devicectl` and `simctl` feed a shared normalized inventory. Keep CoreDevice IDs and hardware UDIDs distinct. Reject ambiguous input and mark offline provenance. Fixtures and hosted tool invocations establish basic behavior. Physical device state, pairing and authorization require hardware validation. |
| Portable source snapshots | Explicit file selection, canonical bounded archive and manifest, expected-digest verification, and extraction into a new owned directory. Paths, links, collisions and quotas are checked. Integrity establishes the bytes being handled. Authentication, build safety and execution permission require separate controls. |
| Offline worker admission and reservations | Check local principal, project, operation, digest, expiry and policy bindings. Use a locked journal for replay rejection and capacity accounting. Release and expiry retain request and nonce history. Claims bind a worker, claim ID and monotonic fence. Expired claims retain capacity until exact-owner recovery records a stopped-worker assertion. |
| Journal maintenance and repair | Migration and compaction retain original events, replay keys, ownership and clock history. Torn manifest and append recovery require durable intent and matching evidence. Repair replays the history, preserves damaged control evidence where applicable, and refuses divergent or unanchored states. Retrying a verified pending append preserves the intended event without duplicating it. |
| Disk and interrupted-write testing | Tests cover process interruption, partial append, native tmpfs `ENOSPC`, persistent ext4 `EDQUOT`, and device-mapper writeback `EIO`. A full ext4 volume returned native sync success in the tested case. The separate injected `ENOSPC` sync case exercised pending repair. Native `EIO` exposed a cache versus disk mismatch. Recovery now reasserts the verified event before sync and verifies replay and owner history across remount. |

The worker foundation assumes a trusted host, clock and state ownership. Production operation still needs authenticated transport and policy sources, revocation at use, external fencing and verified teardown, rollback-resistant storage, and OS-level isolation between execution and signing. Live filesystem gaps include power loss and storage-controller faults, other filesystems and quota types, and Windows ACL and metadata durability checks. ## Test policy and next validation

The repository was made public to clear a GitHub Actions billing admission blocker. For day-to-day work, run focused checks for the changed behavior and its direct callers. If a check fails, fix the failure and rerun that area. Run full regression for user acceptance testing (UAT) and production or public release promotion. GitHub Actions retains its existing push and pull request triggers. Separate hosted runner and Simulator timing failures from product regressions, and record the successful revision and any retries.
